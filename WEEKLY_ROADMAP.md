# VoidRift — Weekly Improvement Roadmap (Aug 3–9, 2026)

Generated by an automated repo audit (tests, lint, and 4 parallel code surveys across
Gameplay, Visual/UX, Social/Competitive, and Monetization). 35 items, 5 per day,
ordered so each day's work is safe to ship independently. Check items off as they land.

**How to use this file:** each daily "improvement loop" session should pick the next
unchecked day's 5 items, implement them, check them off (`[x]`), and commit with a
`Daily improvement loop:` prefix per this repo's existing convention.

## Day 1 — Mon Aug 4 — Crash Fixes & Security-Critical (ship-blocking)

- [ ] 1. **[Gameplay/Bug]** Fix `canvas is not defined` crash — `update()` in `script.js`
      (~line 10929) reads `canvas.width`/`canvas.height` in the Void Nova Orb pickup
      handler, but `canvas` is never declared in that function's scope. Every player
      who picks up a Nova Orb crashes the game loop. Use `dom.canvas` instead.
- [ ] 2. **[Gameplay/Bug]** Fix `selectedShip` used before declaration — `script.js:10221`
      reads a bare `selectedShip` global that is never `let/var/const`-declared and is
      first assigned at `script.js:14129` (hangar init). If the featured-ship hangar
      renders before that init runs, it throws `ReferenceError` and the ship-select
      screen breaks for new installs. Declare it up front with a safe default.
- [ ] 3. **[Gameplay/Bug]** Fix ready-up/countdown state leak — `readyUpPhase` /
      `countdownActive` / `countdownEnd` (`script.js:914-918`) are never reset by
      `resetRuntimeState()` or `startLevel()`. Pausing during the between-wave shop
      and hitting Restart/Exit leaves the shop overlay stuck on screen over a live
      run. Reset these flags wherever runtime state is reset.
- [ ] 4. **[Social/Security]** Add auth verification to `api/friends.js` and
      `api/activity.js` — every action (request/accept/decline/remove/post) currently
      trusts a raw `userId`/`friendId` from the request body with **no token check**,
      unlike `api/leaderboard.js`/`api/users.js` which validate `Authorization: Bearer`.
      Anyone can modify anyone's friend list or post fake activity today.
- [ ] 5. **[Social/Security]** Stop leaking session tokens to console — `auth-system.js:37`
      hardcodes `DEBUG: true`, and `register()`/`login()` log the full backend response
      (including the raw `sessionToken`) to the browser console in production. Gate
      debug logging behind an environment check and redact tokens from any log output.

## Day 2 — Tue Aug 5 — Social/Competitive Hardening

- [x] 6. **[Social/Bug]** Fix friend-request race conditions in `api/friends.js` — all
      mutations are read-modify-write on the KV store with no lock/transaction, so
      concurrent requests can corrupt the friends array. Also add a guard against
      `fromUserId === toUserId` (self-friending).
- [x] 7. **[Social/Bug]** Fix `mark-read` in `api/friends.js` (~line 270) — it currently
      **deletes** the entire notification list instead of flagging entries read,
      destroying notification history. Update in place instead of clearing.
- [x] 8. **[Social/Bug]** Add an idempotency key to leaderboard submission in
      `leaderboard-system.js` / `api/leaderboard.js` — client retries (up to 3x) with
      no dedup key can create duplicate score entries for a single run if a response
      is lost after a successful write.
- [x] 9. **[Social/Bug]** Enforce per-user single-best-score on leaderboards —
      `api/leaderboard.js` `zadd`s a new entry every submission, letting one player
      occupy multiple leaderboard slots. Upsert by user ID, keeping only their best.
- [x] 10. **[Social/Cleanup]** Consolidate the 3 competing session stores
      (`auth-system.js`'s `voidrift_session`, `social-api.js`'s `social_user`, and the
      legacy `void_rift_auth` key still read by `social-hub.js`/`unified-social.js`).
      Four different scripts independently overwrite the login button's `onclick` —
      pick one auth system as the source of truth and remove the others.

## Day 3 — Wed Aug 6 — Monetization Fix (revenue-critical, App Store readiness)

- [ ] 11. **[Monetization/Bug — CRITICAL]** Wire a real ad SDK into
      `ios/VoidRift/Native/AdMobManager.swift` — it is currently a stub whose
      `showRewarded()` always calls `completion(false)`. Combined with `testMode: true`
      and Google's public sample ad unit IDs still in `admob-manager.js:19-20`, the
      shipped app is generating **zero ad revenue** right now.
- [ ] 12. **[Monetization/Bug — CRITICAL]** Register the `iapPurchase`/`iapRestore`
      native message handlers in `ios/VoidRift/Native/GameBridge.swift` — the $2.99
      "Remove Ads" IAP UI in `hangar-ui.js` posts to handler names that don't exist
      natively, so the purchase button silently falls through to "web" and can never
      complete or restore on iOS.
- [ ] 13. **[Monetization/Bug]** Add a session-level rewarded-ad cap — `LAUNCH_PLAN.md`
      specifies "max 2 rewarded ads per session" but no such cap exists; the wave-credit
      ad prompt (`script.js:11237-11285`) can currently fire every 3 waves indefinitely.
- [ ] 14. **[Monetization/Bug]** Fix "ad not ready" handling in `admob-manager.js` (~line
      81) — it immediately fires `onCancelled('not_ready')` instead of queuing/retrying,
      so the "Watch Ad to Continue" revive prompt can dead-end during the ~30s post-death
      preload window, exactly when demand is highest.
- [ ] 15. **[Monetization/Compliance]** Wire an App Tracking Transparency (ATT) consent
      prompt before `AdMobManager.initialize()` — required by Apple before any
      ad-tracking SDK activates; currently only a TODO in `LAUNCH_PLAN.md`.
